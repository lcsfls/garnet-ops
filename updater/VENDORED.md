# The update sidecar (vendored cicd-updater)

This directory is the optional update sidecar of GarnetOps (ADR 0007, ADR 0026): the service that
verifies a signed release, backs up the database, installs the published image digests and rolls
back only when that is provably safe. It is **maintained in this repository**. The upstream
project did not publish an image or a release, so GarnetOps builds, tests, signs and ships the
sidecar itself.

It is an isolated pnpm workspace with its own `package.json`, `pnpm-workspace.yaml` and
`pnpm-lock.yaml`. The root workspace does not include it (see "Why it is isolated").

### Things to know

- The sidecar's own version is the `version` of `packages/sidecar/package.json`, **1.0.0**. The
  image tag and the OCI version label are the GarnetOps release version (the release document
  requires every image tag to equal the release version). `requiresUpdater` in
  `.cicd-updater/release-policy.yaml` is compared with the sidecar's own version.
- The optional self-check (`selfCheck.enabled`, off by default and off in `updater.yaml`) reads the
  release list of the **upstream** repository. Leave it off; it would compare this copy's version
  with upstream's.
- Identifiers inside the protocol keep their upstream spelling: the container label prefix
  `io.github.restow-backup.cicd-updater` (`docker-compose.yml` and the smoke test use it), the `$id`
  of the JSON Schemas, the package name `@restow-backup/cicd-updater` of the SDK.

## Why it is isolated from the root workspace

A separate workspace keeps the sidecar's dependency tree (tsup, vitest 5, TypeScript 6, hono) out
of the application's lockfile, images and audits; keeps upstream's lint style (line width 100,
not 110) and TypeScript settings so upstream patches apply cleanly; and means a root
`pnpm install`, `pnpm typecheck`, `pnpm test` and `biome check` neither build nor test it.
Its checks are their own CI job (`.github/workflows/ci.yml`, job `updater`). The cost is a second
lockfile to keep current: dependency updates for `updater/` are a separate, reviewed change.

The root Biome configuration excludes `updater/` (without it Biome stops with a configuration error,
because the sidecar's `biome.json` is a second root configuration); the sidecar is linted with its own
`biome.json`. The root `Dockerfile` never reads `updater/`, and the root `.dockerignore` keeps it out
of that build context.

## The SDK tarball

The API and the web app use the SDK as `vendor/cicd-updater/restow-backup-cicd-updater-1.0.0.tgz`
(see `vendor/cicd-updater/README.md`). It stays a tarball: pointing the root workspace at
`updater/packages/sdk` would need that package built (`dist/` is not committed) before every
`pnpm install --frozen-lockfile` at the root and in the root `Dockerfile`, and would tie the two
workspaces together. Instead CI checks the tarball against the source: job `updater` builds
`packages/sdk`, packs it and compares every file of `dist/` with the vendored tarball. (The tarball
bytes differ from a fresh pack only in the order of `devDependencies` in its `package.json`, which
pnpm 9 and pnpm 12 write differently; `dist/` is identical.)

## Taking over upstream changes

Upstream is not maintained regularly, so nothing is pulled automatically.

1. Read the upstream commits since the commit above. Treat them as an untrusted contribution:
   the sidecar holds the Docker socket, so a change to `packages/sidecar`, `packages/engine` or
   `docker/` gets the same security review as a change to the API (ADR 0026).
2. Apply the wanted ones as a patch, for example
   `git -C /tmp/cicd-updater-upstream diff <old>..<new> -- packages actions | git apply --directory=updater -p1`;
   regenerate `actions/lib/release-tools.mjs` (`pnpm bundle`) and `THIRD_PARTY_NOTICES`
   (`pnpm notices`), and resolve conflicts in the files listed above by hand.
3. Run, inside `updater/`: `pnpm install --frozen-lockfile`, `pnpm lint`, `pnpm typecheck`,
   `pnpm test:coverage`, `pnpm lint:actions`, `pnpm check:notices`. Check new dependencies against
   the licence list in `AGENTS.md` and add them to `docs/COMPONENTS.md`.
4. Update the commit and date above, and record the change in `CHANGELOG.md` and, if behaviour
   changes, in the ADR.

Changes made here first (fixes) are not sent upstream automatically; offer them upstream if the
project is active again.
